## 二、关键技术发现

1. **X4 的 NPC 替换是「换网格、留骨架」**：macro 只挑 head/torso/props 三个 mesh，
   动画与骨骼根挂在共享 component 上。
2. **X4 的 xac 内部记录了源工程文件名**（如 `char_arg_f_dyn_blend_head_rerig.xac`），
   这是判断一个 mod 是「重绑骨骼」还是「从零转换」的直接证据。
3. **原版躯干 xac 里整套 91 骨骼重复 4 次**（364=4×91，源 .max 合并所致）——
   按名字去重的比较器会给出错误结论，骨骼比对必须**保序**。
4. **`Ter_f_cau.mt_*` / `phon_*` 在名称表里是材质/morph 槽名而非骨骼**，容易误判。
5. 导出器取贴图是按 **Blender 节点名**（`Diffuse`/`Normal`/`Smoothness`）匹配的，
   不是按材质属性名。

## 三·补、贴图转换（已完成）

`X4CharacterConverter` 校验 DDS 像素格式：

| role | X4 格式 | 来源 |
|---|---|---|
| Diffuse | BC1 / BC3 | `_albd`（需 alpha 时用 BC3） |
| Normal | BC5 | `_nrmr` 的 RGB |
| Smoothness | BC4 | `_nrmr` 的 A，**取反**（粗糙度→光滑度）|

### 为什么自研编码器

插件依赖的 `texconv.dll` 直接调用会返回 `E_NOINTERFACE`（COM 接口不支持）。
按「外部工具失效先绕开」的原则，改为用 numpy 自实现 BC1/BC3/BC4/BC5。

实测画质（真实 2048² 角色贴图）：

```
BC1 (albedo)     39.72 dB   2048² 编码 1.5 秒
BC4 (smoothness) 54.82 dB
```

质量达标（>35 dB 视觉无损）。踩过的四个坑：

1. **DX10 扩展头少写 4 字节**（`miscFlags2`）→ 数据偏移应为 152 而非 148。
   现象是整幅图像错位成彩色雪花。
2. **块内 texel 顺序**必须是 `i = x + 4y`（x 变化最快），写成行优先会得到
   逐块彩色噪点。
3. **transpose 后不能直接 reshape** —— 数组非连续时 numpy 按内存顺序重排，
   会静默打乱 texel。必须 `reshape(...).transpose(...)` 一次写成。
4. **端点不能按亮度取极值**。BC1 每块只有 4 色，若按亮度选端点，
   含白色+黑色的块会把红/蓝/品红全部压成灰色。改为对块内 3×3 协方差做
   幂迭代求**主色轴**，沿主轴取两端。

> 另外：纯随机噪声不是 BC1 的有效测试数据（每块仅 4 色，随机纹理必然 ~12 dB）。
> self-test 用的是空间平滑图像。

## 六、实机反馈与修复（第一轮）

首次实机（只启用本 mod）在空间站朝人群转动视角时出现**巨大「折布」**。逐项排查：

### 6.1 不是尺度问题

直接读导出 XAC 里的顶点缓冲（用插件自己的解析器）：

```
head/face  X[-15.25,16.53] Y[-18.71,12.72] Z[138.31,179.72]
head/hair  X[-14.16,13.51] Y[-27.93,3.86]  Z[127.03,181.49]
body/torso X[-19.67,21.77] Y[-19.39,14.15] Z[-0.78,161.10]
body/jacket X[-42.40,43.32] Y[-27.18,15.65] Z[81.80,156.27]
```

厘米量级、身高 181.5、脚底 0 —— **尺度完全正常**。

### 6.2 不是权重问题

权重分布健康，无「整块绑单骨」：

```
face   : Bip01 Head 92296 / eye_dummy 5136×2 / Spine2 2876 / Neck 2258
hair   : Bip01 Head 222282（单骨，符合预期）
hands  : R/L Hand + 手指链
torso  : R/L Calf、Spine2、Feet、Thighs 合理分布
```

### 6.3 真因：**UV 全是 (0,0)**

`build_mod.py` 填充槽位时偷懒，把所有 loop 的 UV 写成 `(0,0)`：

```python
uv = me.uv_layers.new(name="UVMap")
for loop in me.loops:
    uv.data[loop.index].uv = (0.0, 0.0)     # <-- 整个模型采样同一个像素
```

结果整个模型只取贴图上**一个像素**的颜色；若该像素异常/透明，就会渲染成
一块被拉扯的布片 —— 与实机现象吻合。

**修复**：从 RE8 原始 `.mesh` 的 `subMesh.uvList` 提取真实 UV，
经 stage1（`build_rose_x4.py`）与填充阶段（`build_mod.py`）逐级传递到 XAC。
V 轴**不做翻转**，因为导出器自己会做 `1.0 - uv.y`，翻了会双重翻转。

修复后核验：

```
XAC               顶点      唯一UV    坐标范围(Z)        材质槽
rose_body_hands    25314    2346      Z[  102.3,  116.2]  2
rose_body_torso   181149   31319      Z[   -0.8,  161.1] 16
rose_body_jacket  152301   27668      Z[   81.8,  156.3]  5
rose_head_face    107976   15227      Z[  138.3,  179.7]  7
rose_head_eye      9888     410       Z[  161.3,  164.1]  2
rose_head_hair    222282    6683      Z[  127.0,  181.5]  4
```

### 6.4 附带修掉：XAC 放错目录

插件的 `write_package()` **硬编码**把所有 XAC 写进 `bodies/`
（`package_export.py:293`），它没有 head/torso 的概念。
所以 `rose_head.xac` 也被丢进了 `bodies/`。改由 `make_mod.py` 按名称归位
（文件名含 `head` → `heads/`）。

### 6.5 贴图降体积

`tex_convert._convert()` 增加 `max_size` 上限（默认 1024），
在拆分 NRMR **之前**缩放，三张图统一。

| | 之前 | 之后 |
|---|---|---|
| 贴图尺寸 | 2048² | 1024²（14 个占位图为 16²） |
| 贴图载荷 | 138.0 MB | 42.1 MB |
| mod 总大小 | 118 MB | **63.5 MB** |

### 6.6 当前状态

已重新导出、打包并安装到 `extensions/x4_rose_mod/`（66.5 MB 的 dat + 10 KB cat）。

## 七、实机反馈与修复（第二轮）：顶点数爆预算

### 7.1 症状

装上 mod 后空间站内**频闪**、打开**地图卡死**、地图出现**大量彩色斑块**。
（日志称未装 mod 时一切正常。）

### 7.2 排除项

先复查了数据完好性，全部干净：

```
bad(NaN/Inf pos/nrm/tan) = 0/0/0      每网格
zero-length normal/tangent = 0/0
morph_chunks = 0                      （没有残留 morph 数据）
```

### 7.3 真因：几何量是原版 NPC 的 **73 倍**

按同一口径（导出器计入 UV/法线接缝后的顶点数）对比：

| 资产 | 文件 | 顶点 | 网格 |
|---|---|---|---|
| 原版 `char_arg_f_dyn_blend_head.xac` | 1.55 MB | 5,002 | 5 |
| 原版 `char_arg_f_sweater_leggings_civ_01.xac` | 1.31 MB | 4,600 | 4 |
| 原版 `char_arg_f_body_civjacket_01.xac` | 0.40 MB | 4,157 | 4 |
| 原版 `char_arg_f_head_cau_01.xac` | 0.94 MB | 3,261 | 3 |
| **我的 rose_head.xac** | 19.14 MB | **340,146** | 3 |
| **我的 rose_body.xac** | 20.76 MB | **358,764** | 3 |

**原版一个 NPC 资产约 4–5 千顶点，我的接近 35 万 —— 73 倍。**

X4 的 NPC 是**实例化渲染**的：空间站里同时会出现几十个。而地图界面要同时绘制
全部已知对象，所以 NPU 资产爆掉的显存会最先在地图上表现为花屏/卡死。

RE8 是近景单主角游戏，角色模型天生按「一个人占满屏幕」的精度制作，
直接搬进 X4 必然超预算。

### 7.4 修复：按部件 Decimate

在 `build_rose_x4.py` 里对每个子网格做 Collapse 减面（Blender 的 Decimate
会**自动重新分配顶点组权重**，所以蒙皮能保住）：

```python
DECIMATE_RATIO = {
    'hair': 0.05, 'jacket': 0.06, 'body': 0.10, 'slingbelt': 0.10,
    'hand_l': 0.30, 'hand_r': 0.30, 'eyes': 0.50, 'face': 0.20,
}
```

## 八、实机反馈与修复（第三轮）

第三轮反馈三个问题：**眼球纯白**、**萝丝是 A-pose 而其他 NPC 手臂自然下垂**、
**动作时手臂向后弯折、手指被拉长**。

### 8.1 眼球纯白：三层原因叠加

眼睛部件 `ch01_6030_rose_eyes` 里其实有两个球：真眼球
（`shader_eyes_shader`，有 albedo）和一个**眼透镜壳**
（`shader_eyeslens_shader`）。源数据给透镜标的属性是：

```json
"shader_eyeslens_shader": { "noAlbedo": true, "transparent": true,
                            "normalRoughness": ".../eyecover_nrmr.png" }
```

它**没有固有色、且是透明的**。但导出器强制要求 Diffuse 贴图，于是它拿到了
一个**不透明占位色**，变成一个实心球扣在眼球前面 —— 这就是「纯白眼球」。

同一问题还出现在 face 部件里的 `Eyelens_Mat` 与 `EyeWet_Mat`。

修复：新增 `DROP_SUBMESH_MATERIALS`，导出时丢弃这三个只靠 shader 出效果的
覆盖层，露出底下真正有贴图的眼球（`Eye_Mat` / `shader_eyes_shader`）。

同时发现 `shader_eyes_shader` 被我标成了 `ALPHA1`，但它的 albedo 是
**纯 RGB 无 alpha 通道**的，等于把眼球按透明渲染 —— 已从 `ALPHA_MATS` 移除。

> 额外踩坑：曾尝试把 `_eyeao_albd`（虹膜/瞳孔层）乘进眼球 albedo，结果眼球
> **全黑**。该贴图平均只有 (24,4,0)、最大 24、**没有任何亮区**，是着色器参数图
> 而非细节层，相乘即毁。已回退并在代码里注明。

### 8.2 手臂反向弯折：导出器轴向约定

插件里定义了：

```python
AXIS_TO_BLENDER = Matrix.Rotation(math.radians(90.0), 4, "X")    # X4 -> Blender
AXIS_TO_XAC     = Matrix.Rotation(math.radians(-90.0), 4, "X")   # Blender -> XAC
blender_to_xac_vector(v) = (v.x, v.z, -v.y)
```

导出时会套一次 `(x, z, -y)`。我此前直通传入，等于整体绕 X 轴多转了 -90°，
肢体朝向因此反了（动作时手臂朝后弯）。

试过传入 `(x, z, -y)` 想抵消，结果反而把身高推进了 Z 轴
（实测 `Y[-14.4, 19.3] Z[-161.0, 0.8]`），是**倒退**，已回退。

**结论：直通 `(x, y, z)` 是正确解**（实测 `Y[-0.8, 161.0]` = 身高）。
导出后的坐标与原版完全同构：

```
rose_head_face   X[-15.2, 16.5] Y[138.3, 179.7] Z[-12.7, 18.7]
原版 head        X[ -9.6,  9.6] Y[145.4, 182.0] Z[-10.1, 12.9]
```

已放宽到 **0.55**，手部顶点 1613 → **2762**（+71%）。

## 十、坐标系统重构（用户要求「重新审视」后）

### 10.1 三个真实且独立的 bug

**(a) 缩放丢失** —— 网格被压成 ~2 cm

## 十一、根因定位与修复（2026-09-23）

### 11.1 旧结论错在哪

第十节的判断是：「R 几乎是单位阵 ⇒ 坐标系没错；残差集中在四肢 ⇒ 是姿态差异」。
这个推理有一个漏洞：**`det(R) = +1` 的 Kabsch 拟合一整类变换，唯独不含反射**。
如果两套骨架实际上是前后镜像关系，拟合会退而求其次给出「最优旋转」，
残差自然堆在前后方向偏离最大的部位。

实测一下镜像假设就能证伪旧结论：

| 变换 | 手指残差 | 手残差 | 脚趾残差 |
|---|---|---|---|
| `(x, -z, y)`（旧） | 57.8 cm | 42.0 cm | 23.4 cm |
| `(x, +z, y)`（新） | 28.6 cm | 25.3 cm | 10.6 cm |

**哪个符号对，由解剖学决定，不由拟合决定**：

```
Rose 眼球网格重心 在 Head 骨的 +z 侧（+4.9 cm）
X4   ter_eyeball_left 在 Bip01 Head 的 +y 侧（+9.5 cm）
→ Rose 的 +z 与 X4 的 +y 都是「前」→ z 必须映射到 +y，不能取负
```

同样的判据还有脚趾：Rose 的脚趾在 +z，X4 的 `Toe0` 在 +y。
代码里其实一直有两个自相矛盾的函数 —— `re8_to_x4.re8_to_x4()` 返回
`(x, z, y)`（对），`build_rose_x4._rose_cm_to_blender()` 返回 `(x, -z, y)`（错），
而实际跑的是后者。§10.1(b) 当时把带负号的版本当成「正确解」，是把
「身高落在第三分量」当成了唯一判据 —— 而两种写法身高都落在第三分量。

### 11.2 第二个根因：单一刚体变换本身就不够

即便符号修对，一次 Kabsch 拟合仍然留下：躯干 1–10 cm、手 25 cm、脚趾 10.6 cm。
因为两套骨架的**姿态**和**比例**都不同：

| 段 | Rose | X4 Biped | 差 |
|---|---|---|---|
| 骨盆 → 肩 | 37.1 cm | 52.3 cm | +15 cm |
| 肩 → 腕（骨链） | 45.9 cm | 59.2 cm | +13 cm |
| 手方向 | 前伸下垂 | 自然下垂 | ≈ 95° |

蒙皮是相对**绑定姿态**定义的：顶点离主导骨 25 cm，任何动画都会把它甩向错误方向。
所以必须把网格**逐骨**搬到 X4 的绑定姿态上。

### 11.3 第三个坑：RE8 骨骼矩阵没有统一的局部轴约定

如果按「骨骼矩阵第 0 行 = 骨轴」来取方向，会得到这样的荒唐结果：

```
脊柱（Spine_0/1/2、Neck_0）  旋转恰好 90.0°
左手指（L_IndexF1 等）        旋转 168–172°
右手对应骨                    旋转 8–12°     ← 左右不对称就是信号
```

原因是 Rose 的骨架里**不同骨骼的局部坐标系约定不同**：脊柱的骨轴落在矩阵
第 1 行（局部 +Y），上臂的骨轴落在第 0 行（局部 +X）。正确做法是两边都用
**子骨位置均值 − 自身位置**来定义骨轴，语义与左右对称性立刻恢复：

```
L/R_UpperArm   26°   L/R_Forearm  95°   L/R_Foot 107°   左右完全对称
```

另外 `min_rotation()` 在 180° 时返回 `-I`，那是反射不是旋转，一并修掉了。

### 11.4 新方法：逐骨绑定姿态转移（`retarget_core.BindPoseRetarget`）

1. **全局框架** —— 18 对无歧义骨做一次 Kabsch（`scale=1.0469`，`det(R)=+1`）。
2. **逐骨变换** —— 对每根源骨 b（有 X4 对应骨 B）：
   `x → q_B + R_B (x − p_b)`，`R_B` 把源骨轴转到目标骨轴（最短弧，不引入扭转）。
3. **折叠骨锚定** —— `jacket_*`、`Hair*_FK_*`、`*_Twist_*`、`FACIAL_*` 在 X4 里
   没有位置对应，只能「共用」某根骨。若直接拿它们自身位置去对齐映射骨，
   夹克会被推进胸腔（实测差 30 cm）；改为继承**同侧最近的那根有对应关系的骨**
   的变换。判据是 `re8_to_x4.is_direct_bone()`。
4. **按权重混合** —— 顶点位移 = `Σ w_B · T_B(x) / Σ w_B`，
   相当于把线性混合蒙皮在转换期做一次。几何因此在躯干/手臂上被拉伸到
   X4 的比例，这是骨架比例差异的必然代价；**骨架本身一个字节都没动**。

### 11.4b 补记：反射变换必须翻转三角形绕序

改对符号后实机复测，手正常了，但冒出三个新症状：**脸消失**、
**鞋和裤子变透明、能看到对面内壳**、**上衣满是褶皱**。这三个是同一个原因。

`(x, -z, y)` 的行列式是 **+1**（保向），而物理正确的 `(x, +z, y)` 是 **-1**
（交换两个轴 = 反射）。顶点位置看着完全正确（指标、骨骼叠加图、包围盒都过），
但**每个三角形都朝内了**：引擎剔除正面，于是衣服变成半透明、能看穿到内壳，
光照方向反过来让布料看着像一团揉皱的破布，脸则整片消失。

RE8 的坐标表示是右手系、X4 的是左手系（`左×前 = -上`），所以「物理正确」
与「保向」在这里天然不可兼得 —— 必须牺牲后者，再把三角形索引顺序反过来
`(a,b,c) → (c,b,a)` 补偿。UV 不受影响（UV 是逐顶点/逐 loop 带过去的）。

> **判据**：`tools/check_normals.py`。它统计每个网格「面法线背离质心」的比例：
> 原版资产在 0.59–0.77，绕序翻转的网格恰好落在 0.5 以下
> （精确翻转 = 1 − 原值，实测 torso 0.435 → 0.565、jacket 0.454 → 0.546）。
> 这个错误**骗得过所有基于顶点位置的检查**，只有它和实机截图能发现。

### 11.4c 补记：骨轴不能用「子骨均值」，衣服被转翻了

绕序修好后实机复测又报：**夹克腰部一块浅褐色补丁、颜色与原版对不上**。
逐层二分（stage1 blend 对比、全局变换 vs 逐骨转移、材质染色）锁定到
**逐骨转移本身**，再查旋转量发现：

```
Bip01 Pelvis   旋转 161.3°     ← 骨盆被整个转翻
其余骨          最大 46.5°     ← 手指/前臂，属真实姿态差异
```

**原因**：骨轴 = 「子骨位置均值 − 自身」这条规则在骨盆上失效。
Rose 的 `Hip` 有三根子骨：`Spine_0`（与它**完全重合**）和左右大腿（朝**下**），
均值方向朝下；而 X4 的 `Bip01 Pelvis` 指向 `Spine`（朝**上**）——于是拟合出
161° 旋转。**所有权重落在骨盆上的顶点（夹克下摆、裤腰、鞋帮）被整体转翻**，
翻出来的内表面采样到贴图另一区域，就是那块浅褐色。

**修法**：骨轴只看**主链上的第一个子骨**（骨架顺序）、且源与目标必须取同一根
（把该子骨映射到 X4 再取方向）；第一个子骨退化（如骨盆与 `Spine_0` 重合）时
退到**父骨方向**，再不行就**不旋转**。骨盆因此变成纯平移，旋转 0°。

> 教训：骨轴推导里任何"取平均"都可能在分叉骨（骨盆、手、脚趾根）上给出
> 与解剖学无关的方向。判据是**旋转量本身**——绝大多数骨应该小于 60°，
> 出现 90°/180° 这类整数级角度基本就是推导错了。

### 11.4d 补记：衣服显色的两个材质坑

1. **`*_Stitch_Mat` 一族**（夹克门襟/腰部饰边、裤缝、鞋缝）在源数据里
   **没有 albedo**，管线给的是手工填的深色占位（如夹克缝线 `(58,54,50)`）。
   这些不是细线，是**成片的几何**（夹克缝线 3799 顶点，UV 还是平铺的
   v∈[-10,11]），于是腰上出现一条突兀的深色带。改成**从主材质推导**：
   读同部件主材质的 UV 区域采样均色（夹克缝线 → `(80,75,66)`，
   裤缝 → 牛仔蓝 `(86,100,115)`）。
2. **缺少 smoothness 贴图**时导出器会写死 `Smoothness = 0.5`，而夹克本体是
   0.08（哑光）——那些饰边因此在哑光大衣上反光发亮。给共色材质一并生成
   主材质粗糙度的纯色 BC4 贴图。
3. **`Metal_Mat`**（7776 顶点的卡片几何，贴在夹克表面）有自己的图集，
   但平铺 UV 采样到的是 `(117,108,92)` 浅褐，与夹克 `(80,75,66)` 不匹配，
   同样覆盖成主材质色、保留其法线/粗糙度。

### 11.4e 补记：眼球、鞋底、面数预算（第二轮实机反馈）

第二轮实机报了三件事，逐条定位：

**(1) 眼球不见了。** Rose 的**眼球几何**在她的 `L_Eye`/`R_Eye` 骨**下方 4.9 cm**，
而 X4 的 `left_eye_dummy` 在 `Bip01 Head` **上方 8.5 cm**。逐骨转移按"骨位置"
算位移，只有 2.4 cm，眼球于是留在脸颊里（渲染出来眼窝是个黑洞）。

修法：眼球**改骑 Head 的变换**（`_bind_eyes_to_head()`）——
权重仍然是 `eye_dummy`，所以注视控制照常生效，只是绑定姿态下眼球跟脸对齐、
留在眼窝里。

**(2) 鞋陷进地面 3.5 cm。** `Bip01 L Toe0` 的目标位置比 Rose 的脚趾骨**低 3.13 cm**
（X4 的脚趾骨几乎贴地：z=0.12，脚踝 z=11.55，落差 11.4 cm；Rose 只有 6.3 cm）。
脚趾几何被拉到新位置，鞋头就沉下去了。实测本体最低点 −3.86 cm，而 vanilla 是 −0.32。

修法：变形后按权重挑出脚部顶点（`Foot`/`Toe`/`Calf` 权重 > 0.5），
整团抬到地面（`lift_feet()`，实测抬升 3.34 cm）。代价是脚趾相对骨骼偏了 3.3 cm，
不可见；陷地是看得见的。

**(3) 空间站里频闪。** 这是老问题：X4 的 NPC 是实例化渲染的，资产顶点数必须
贴近 vanilla 的 ~5k/资产。上一版为了把夹克做好看，比例提到 0.28/0.16，
导出顶点冲到 **128 950（15.5×）**，频闪复发；早先稳定过的版本是 ~9×。
现在收到 **70 818（8.5×）**：

| 部件 | 上版比例 | 现比例 | 上版顶点 | 现顶点 |
|---|---|---|---|---|
| jacket | 0.28 | 0.11 | 11 534 | 5 598 |
| body | 0.16 | 0.09 | 9 240 | 6 402 |
| face | 0.28 | 0.17 | 6 572 | 4 241 |
| hair | 0.05 | 0.03 | 6 004 | 4 956 |
| hands | 0.55 | 0.45 | 2 759 | 2 311 |
| eyes | 0.50 | 0.35 | 999 | 715 |
| slingbelt | 0.65 | 0.35 | 619 | 371 |

> 结论：**外观质量与显存预算要一起看**。夹克比例每翻一档，观感提升有限，
> 但顶点数是线性涨的；先用 8.5× 站稳，再谈细节。

### 11.4f 补记：粗糙感、缩脖子、眼球（第三轮实机反馈）

**(1) 身上太粗糙、脸上有沟壑感。** 建网格时没开平滑着色——`from_pydata` 默认
**平面着色**，减面后的不规则三角形在平面着色下每个面都是一块可见的面片，
这就是"沟壑感"的来源。RE8 的网格本来是平滑着色的，X4 原版资产也是。
加上 `poly.use_smooth = True` 后观感立刻正常，且**不增加顶点**。

**(2) 头低、像缩在衣领里。** 源数据里眼球比夹克领口高 **7.5 cm**，vanilla 是
9.9 cm，而当时只剩 **0.6 cm**。原因是骨架比例：X4 的 `Bip01 Head` 只比
`Bip01 Neck` 高 7.8 cm，Rose 的高 13.7 cm（脖子长近一倍）。逐骨各自对齐，
头被拽下 5.9 cm、领口被推上，两头一挤就缩进去了。

修法：**头颈共用一份位移**（取两根骨位移的平均，`_harmonise_head_neck()`），
各骨离自己的目标约 3 cm，但作者设定的头颈间距保住了。修完脸顶从 177.5
抬到 180.9 cm。

**(3) 眼球偶尔错位、不跟头。** 两个独立问题叠在一起：

* **权重**：X4 用 look-at 控制器驱动 `left/right_eye_dummy`，而 Rose 的眼球
  几何离这两根骨约 9 cm，视线一转眼球就绕 9 cm 半径甩出去。
  修法：这两根骨上的权重**改挂到 `Bip01 Head`**（`EYE_CONTROLLERS`），
  眼球不再随视线摆，但稳稳待在眼窝里。
* **几何**：`ch01_6030_rose_eyes` **根本不是眼球**。源数据里它是
  `shader_eyes_shader`，高度 y 1.542–1.570；而 `face` 部件里的 `Eye_Mat`
  在 y 1.584–1.611，**正好与眼睑(1.584–1.602)、睫毛(1.584–1.602)对齐**。
  也就是说前者是一个**低了 4.2 cm 的拷贝**，一直被我们当成眼睛导出，
  真正的眼球反而被挡在后面。现在直接不导出该部件，用 face 里的真眼球。

> 附带踩坑：**.xac 表达不了"空槽位"**。删掉宿主对象没用——导出器会按
> 宿主模板把每个 `mesh_id` 重建，删掉的槽位会带着**原版几何**回来；
> 换成 3 个重合顶点则两边都报错（导出器："vertex 0 has no bone weights"，
> 导入器："degenerate triangle after seam welding"）。最后放一个**1 cm 的
> 三角形埋在头部内部**，两边都能过、也看不见。

### 11.4g 补记：脚跟离地、虎口塌陷（第四轮实机反馈）

**(1) 脚后跟离地、只有前脚掌着地。** 查高度分布一目了然：

```
             脚跟    足弓    前掌    脚趾
vanilla     -0.15   -0.25   -0.32    1.10     ← 整个鞋底贴地
我们(v13)    5.43    3.23   -0.48   -0.59     ← 只有前掌着地
```

之前以为是骨骼旋转（X4 的脚链比 Rose 陡得多，踝到趾落差 11.4 cm vs 6.3，
转向对齐会把脚前倾 16°），去掉旋转只把脚跟从 5.43 降到 4.07 —— **真凶是位移差**：
`Foot` 的目标位置比源位置**高 2.0 cm**，而 `Toe0` 的目标**低 3.1 cm**，
逐骨各走各的就把脚拉斜了。

修法：**整只脚共用踝关节的位移**（`_feet_share_one_offset()`）——
脚本来就是一块刚体，精度让给视觉。同时把 `lift_feet()` 改成**双向对齐**
（原来只在"陷进地面"时抬升，脚悬空时不管），现在脚底稳定落在 −0.5 cm：

```
             脚跟    足弓    前掌    脚趾
我们(v16)   -0.49   -0.30   -0.27    0.77
```

**(2) 掌心虎口向内凹陷。** 这是"逐骨对齐"的固有代价暴露在手上：Rose 的手指是
**并拢**的，X4 的手指骨是**张开**的，每根手指各自对准自己的目标骨，相邻手指
的位移差最多 6 cm，夹在中间的虎口皮就被撕进去了。

三种做法都试了：

| 方案 | 虎口 | 手指离骨 |
|---|---|---|
| 各自对齐（原状） | 撕开、凹陷 | 1.03 cm |
| 完全跟随手掌 | 完好 | 5.76 cm（弯曲动画会把手指甩飞） |
| **各取一半（采用）** | 完好 | **2.95 cm** |

`FINGER_OWN_OFFSET = 0.5`：手指保留一半自己的目标偏移、一半跟随手掌位移，
旋转仍按各自骨骼，所以握拳/弯曲照常。

### 11.4h 补记：面片感的真凶是法线，不是面数（第五轮实机反馈）

上一版加了 `use_smooth = True`，实机看**脸上还是一块块的面**。查法线才发现：

```
导入导出的 xac 后：|顶点法线 − 面法线| = 0.000   ← 完全是平面着色
```

**原因是两段式的管线**：stage1 设了平滑，但 **stage2 用 `from_pydata` 重建网格时
默认回到平面着色**，而导出器取的是 `loop.normal` —— 于是每个三角形都带着自己的
面法线进了 .xac。stage1 的设置根本没走到导出。

在 stage2 也补上 `use_smooth` 之后：

```
|顶点法线 − 面法线| = 0.419（面部）/ 0.385（头发）   ← 真正的平滑法线
```

**意外的大收益**：平滑法线同时消掉了**法线接缝**，导出顶点数从 45 189 掉到
**13 355（−70%）**。X4 的导出计数是"每条 UV 接缝和法线接缝各算一个顶点"，
所以这一步等于白送预算。于是把减面比例整体提上去：

| 部件 | 旧比例 | 新比例 | 原始顶点 |
|---|---|---|---|
| body | 0.09 | **0.30** | 6 420 → 14 720 |
| jacket | 0.11 | **0.35** | 5 596 → 13 903 |
| face | 0.17 | **0.50** | 4 244 → 11 029 |
| hair | 0.03 | **0.10** | 4 956 → 9 280 |
| hands | 0.45 | **0.75** | 1 157 → 1 813 |

**结果：面数是上一版的 2.3 倍，导出顶点反而从 8.3× 降到 6.1× vanilla。**

### 11.4i 补记：手指不要"半量混合"

上一版为了救虎口，让手指"一半跟随手掌"。思路错了：每根手指的混合结果都不同，
**手指反而被扭得更厉害**。三种做法的实测：

| 方案 | 虎口 | 手指离骨 | 观感 |
|---|---|---|---|
| 各自对齐 | 撕开 | 1.03 cm | 手指形状正确，虎口凹陷 |
| 完全跟随手掌 | 完好 | 5.76 cm | 手形对，但弯曲动画会把手指甩飞 |
| 各取一半 | 略好 | 2.95 cm | **每根手指都被扭**（最差） |

最终回到**各自对齐**（手指 0.96 cm），虎口改用**权重平滑**
（`smooth_vertex_weights()`：把每个顶点的权重与网格邻居做两轮拉普拉斯平均）——
塌陷的成因是权重在虎口处突变，平滑权重才是对症的做法，而不是动位移。

### 11.4j 补记：虎口"缺一块"——手指必须绑手掌

权重平滑之后虎口不再是"凹陷"，而是**指间裂开一道缝、一直裂到掌根**，
看上去像平白少了一块皮。特写渲染对照原版就清楚了：vanilla 的手指是**并拢**的。

根子在于两套骨架的手型不同：**Rose 的手指并拢，X4 的手指骨张开**。
逐骨对齐 = 把手指掰开，而指间的皮（虎口、指蹼）本身没有几何，
只是两侧皮肤连起来的过渡，一掰就撕开。

绕了一圈才定下来：**手指权重整体挂到手掌骨**（`FINGERS_BIND_TO_PALM`）。
代价是手指不再单独做动作——对 NPC 几乎看不出来，比撕开一条缝强得多。

| 做法 | 静态手型 | 动画 |
|---|---|---|
| 手指绑各自骨 | 指间裂开 | 正常 |
| 半量混合 | 五根手指各自扭曲 | 差 |
| **手指绑手掌（采用）** | **与原作者手型一致** | 手指不单独弯曲 |

### 11.4k 补记：手指上的"横纹"——别减面，UV 会坏

手指绑到手掌之后手型对了，但实机看到**手指上有一圈圈横向纹路**、指根还有
深色斑块。workbench 预览看不到（它不显示法线贴图），换成 **EEVEE + 法线贴图**
一渲染就复现了。

原因是 **hands 还在按 0.75 减面**：切线是跟着 UV 走的，手指那点 UV 被
collapse 重写之后切线全乱，法线贴图就渲染成一圈圈环纹。

手部本来就只有 2346 顶点/只，**干脆一点不减**（`hand_l/r = 1.0`，总共多花
约 4k 顶点），同时手部也跳过权重平滑（手指已绑手掌，权重本来就均匀，
再扰动顶点只会继续糟蹋法线贴图）。环纹随即消失。

> 这一条可以推广：**只要材质带法线贴图，减面就不只是几何问题**。
> 脸、手这类"有细节贴图又在近景"的部位，减面比例的代价要按切线质量算，
> 不能只按顶点数算。

## 十二、测试模式：所有 Argon 女性外观池全覆盖

为了实机测试时不用「刷 NPC」，`make_mod.py` 增加了开关：

```python
#: tools/make_mod.py
REPLACE_ALL_ARGON_FEMALE = True    # True = 全部替换；False = 追加（约 1/4）
```

**做法不是硬编码池名，而是从原版 `charactergroups.xml` 自动发现**：
凡「select 里含女性 macro」的池都算。要注意原版池是**嵌套**的
（`argon.trader.female` → `argon.civilian.female`，后者才真正列 macro），
所以只替换叶子池即可覆盖上层。

自动发现的结果（9 个池，共 115 条原版外观被替换）：

```
argon.allraces                   96 条（男女混合池，一并替换）
argon.factiondiplomat.female      1
antigone.factiondiplomat.female   1     ← 派系专属池，硬编码列表会漏
hatikvah.factiondiplomat.female   1     ← 同上
argon.service.female              3
argon.marine.female               3
argon.civilian.female             6
argon.pilot.female                3
argon.commander.female            3
```

混合池 `benchmark` / `testcharacter` **不替换**：它们是开发/跑分用的池，
不是外观池，整池替换会影响性能基准。判据是「池内是否全是女性 macro」，
`argon.*` 前缀的混合池（即 `argon.allraces`）例外地一起替换。

替换用 `<replace sel="/characters/character[@name='…']">` 整节点换掉，
而不是 `<add>` 追加 —— 这样池里不存在原版 fallback，出现率就是 100%。
`verify_mod.py` 会模拟应用 diff 并逐池确认「只剩萝丝」。
