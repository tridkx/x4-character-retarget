## 二、关键技术发现

1. **X4 的 NPC 替换是「换网格、留骨架」**：macro 只挑 head/torso/props 三个 mesh，
   动画与骨骼根挂在共享 component 上。
2. **X4 的 xac 内部记录了源工程文件名**（如 `char_arg_f_dyn_blend_head_rerig.xac`），
   这是判断一个 mod 是「重绑骨骼」还是「从零转换」的直接证据。
3. **原版躯干 xac 里整套 91 骨骼重复 4 次**（364=4×91，源 .max 合并所致）——
   按名字去重的比较器会给出错误结论，骨骼比对必须**保序**。
4. **`Ter_f_cau.mt_*` / `phon_*` 在名称表里是材质/morph 槽名而非骨骼**，容易误判。
5. 导出器取贴图是按 **Blender 节点名**（`Diffuse`/`Normal`/`Smoothness`）匹配的，
   不是按材质属性名。

## 三·补、贴图转换（已完成）

`X4CharacterConverter` 校验 DDS 像素格式：

| role | X4 格式 | 来源 |
|---|---|---|
| Diffuse | BC1 / BC3 | `_albd`（需 alpha 时用 BC3） |
| Normal | BC5 | `_nrmr` 的 RGB |
| Smoothness | BC4 | `_nrmr` 的 A，**取反**（粗糙度→光滑度）|

### 为什么自研编码器

插件依赖的 `texconv.dll` 直接调用会返回 `E_NOINTERFACE`（COM 接口不支持）。
按「外部工具失效先绕开」的原则，改为用 numpy 自实现 BC1/BC3/BC4/BC5。

实测画质（真实 2048² 角色贴图）：

```
BC1 (albedo)     39.72 dB   2048² 编码 1.5 秒
BC4 (smoothness) 54.82 dB
```

质量达标（>35 dB 视觉无损）。踩过的四个坑：

1. **DX10 扩展头少写 4 字节**（`miscFlags2`）→ 数据偏移应为 152 而非 148。
   现象是整幅图像错位成彩色雪花。
2. **块内 texel 顺序**必须是 `i = x + 4y`（x 变化最快），写成行优先会得到
   逐块彩色噪点。
3. **transpose 后不能直接 reshape** —— 数组非连续时 numpy 按内存顺序重排，
   会静默打乱 texel。必须 `reshape(...).transpose(...)` 一次写成。
4. **端点不能按亮度取极值**。BC1 每块只有 4 色，若按亮度选端点，
   含白色+黑色的块会把红/蓝/品红全部压成灰色。改为对块内 3×3 协方差做
   幂迭代求**主色轴**，沿主轴取两端。

> 另外：纯随机噪声不是 BC1 的有效测试数据（每块仅 4 色，随机纹理必然 ~12 dB）。
> self-test 用的是空间平滑图像。

## 六、实机反馈与修复（第一轮）

首次实机（只启用本 mod）在空间站朝人群转动视角时出现**巨大「折布」**。逐项排查：

### 6.1 不是尺度问题

直接读导出 XAC 里的顶点缓冲（用插件自己的解析器）：

```
head/face  X[-15.25,16.53] Y[-18.71,12.72] Z[138.31,179.72]
head/hair  X[-14.16,13.51] Y[-27.93,3.86]  Z[127.03,181.49]
body/torso X[-19.67,21.77] Y[-19.39,14.15] Z[-0.78,161.10]
body/jacket X[-42.40,43.32] Y[-27.18,15.65] Z[81.80,156.27]
```

厘米量级、身高 181.5、脚底 0 —— **尺度完全正常**。

### 6.2 不是权重问题

权重分布健康，无「整块绑单骨」：

```
face   : Bip01 Head 92296 / eye_dummy 5136×2 / Spine2 2876 / Neck 2258
hair   : Bip01 Head 222282（单骨，符合预期）
hands  : R/L Hand + 手指链
torso  : R/L Calf、Spine2、Feet、Thighs 合理分布
```

### 6.3 真因：**UV 全是 (0,0)**

`build_mod.py` 填充槽位时偷懒，把所有 loop 的 UV 写成 `(0,0)`：

```python
uv = me.uv_layers.new(name="UVMap")
for loop in me.loops:
    uv.data[loop.index].uv = (0.0, 0.0)     # <-- 整个模型采样同一个像素
```

结果整个模型只取贴图上**一个像素**的颜色；若该像素异常/透明，就会渲染成
一块被拉扯的布片 —— 与实机现象吻合。

**修复**：从 RE8 原始 `.mesh` 的 `subMesh.uvList` 提取真实 UV，
经 stage1（`build_rose_x4.py`）与填充阶段（`build_mod.py`）逐级传递到 XAC。
V 轴**不做翻转**，因为导出器自己会做 `1.0 - uv.y`，翻了会双重翻转。

修复后核验：

```
XAC               顶点      唯一UV    坐标范围(Z)        材质槽
rose_body_hands    25314    2346      Z[  102.3,  116.2]  2
rose_body_torso   181149   31319      Z[   -0.8,  161.1] 16
rose_body_jacket  152301   27668      Z[   81.8,  156.3]  5
rose_head_face    107976   15227      Z[  138.3,  179.7]  7
rose_head_eye      9888     410       Z[  161.3,  164.1]  2
rose_head_hair    222282    6683      Z[  127.0,  181.5]  4
```

### 6.4 附带修掉：XAC 放错目录

插件的 `write_package()` **硬编码**把所有 XAC 写进 `bodies/`
（`package_export.py:293`），它没有 head/torso 的概念。
所以 `rose_head.xac` 也被丢进了 `bodies/`。改由 `make_mod.py` 按名称归位
（文件名含 `head` → `heads/`）。

### 6.5 贴图降体积

`tex_convert._convert()` 增加 `max_size` 上限（默认 1024），
在拆分 NRMR **之前**缩放，三张图统一。

| | 之前 | 之后 |
|---|---|---|
| 贴图尺寸 | 2048² | 1024²（14 个占位图为 16²） |
| 贴图载荷 | 138.0 MB | 42.1 MB |
| mod 总大小 | 118 MB | **63.5 MB** |

## 七、实机反馈与修复（第二轮）：顶点数爆预算

### 7.1 症状

装上 mod 后空间站内**频闪**、打开**地图卡死**、地图出现**大量彩色斑块**。
（日志称未装 mod 时一切正常。）

### 7.2 排除项

先复查了数据完好性，全部干净：

```
bad(NaN/Inf pos/nrm/tan) = 0/0/0      每网格
zero-length normal/tangent = 0/0
morph_chunks = 0                      （没有残留 morph 数据）
```

### 7.3 真因：几何量是原版 NPC 的 **73 倍**

按同一口径（导出器计入 UV/法线接缝后的顶点数）对比：

| 资产 | 文件 | 顶点 | 网格 |
|---|---|---|---|
| 原版 `char_arg_f_dyn_blend_head.xac` | 1.55 MB | 5,002 | 5 |
| 原版 `char_arg_f_sweater_leggings_civ_01.xac` | 1.31 MB | 4,600 | 4 |
| 原版 `char_arg_f_body_civjacket_01.xac` | 0.40 MB | 4,157 | 4 |
| 原版 `char_arg_f_head_cau_01.xac` | 0.94 MB | 3,261 | 3 |
| **我的 rose_head.xac** | 19.14 MB | **340,146** | 3 |
| **我的 rose_body.xac** | 20.76 MB | **358,764** | 3 |

**原版一个 NPC 资产约 4–5 千顶点，我的接近 35 万 —— 73 倍。**

X4 的 NPC 是**实例化渲染**的：空间站里同时会出现几十个。而地图界面要同时绘制
全部已知对象，所以 NPU 资产爆掉的显存会最先在地图上表现为花屏/卡死。

RE8 是近景单主角游戏，角色模型天生按「一个人占满屏幕」的精度制作，
直接搬进 X4 必然超预算。

### 7.4 修复：按部件 Decimate

在 `build_rose_x4.py` 里对每个子网格做 Collapse 减面（Blender 的 Decimate
会**自动重新分配顶点组权重**，所以蒙皮能保住）：

```python
DECIMATE_RATIO = {
    'hair': 0.05, 'jacket': 0.06, 'body': 0.10, 'slingbelt': 0.10,
    'hand_l': 0.30, 'hand_r': 0.30, 'eyes': 0.50, 'face': 0.20,
}
```

五官（`face`）留更高比例以保住轮廓；头发/夹克几乎不承载结构，压得最狠。
另设 `DECIMATE_FLOOR = 200`：减完不足 200 顶点的极小网格回退为原始网格，
避免被削成空壳。

效果：

|---|---|---|---|
| body | 38,635 | 6,751 | 0.10 |
| jacket | 33,741 | 3,745 | 0.06 |
| face | 20,448 | 4,890 | 0.20 |
| hair | 52,124 | 6,004 | 0.05 |

## 八、实机反馈与修复（第三轮）

第三轮反馈三个问题：**眼球纯白**、**萝丝是 A-pose 而其他 NPC 手臂自然下垂**、
**动作时手臂向后弯折、手指被拉长**。

### 8.1 眼球纯白：三层原因叠加

眼睛部件 `ch01_6030_rose_eyes` 里其实有两个球：真眼球
（`shader_eyes_shader`，有 albedo）和一个**眼透镜壳**
（`shader_eyeslens_shader`）。源数据给透镜标的属性是：

```json
"shader_eyeslens_shader": { "noAlbedo": true, "transparent": true,
                            "normalRoughness": ".../eyecover_nrmr.png" }
```

它**没有固有色、且是透明的**。但导出器强制要求 Diffuse 贴图，于是它拿到了
一个**不透明占位色**，变成一个实心球扣在眼球前面 —— 这就是「纯白眼球」。

同一问题还出现在 face 部件里的 `Eyelens_Mat` 与 `EyeWet_Mat`。

修复：新增 `DROP_SUBMESH_MATERIALS`，导出时丢弃这三个只靠 shader 出效果的
覆盖层，露出底下真正有贴图的眼球（`Eye_Mat` / `shader_eyes_shader`）。

同时发现 `shader_eyes_shader` 被我标成了 `ALPHA1`，但它的 albedo 是
**纯 RGB 无 alpha 通道**的，等于把眼球按透明渲染 —— 已从 `ALPHA_MATS` 移除。

> 额外踩坑：曾尝试把 `_eyeao_albd`（虹膜/瞳孔层）乘进眼球 albedo，结果眼球
> **全黑**。该贴图平均只有 (24,4,0)、最大 24、**没有任何亮区**，是着色器参数图
> 而非细节层，相乘即毁。已回退并在代码里注明。

### 8.2 手臂反向弯折：导出器轴向约定

插件里定义了：

```python
AXIS_TO_BLENDER = Matrix.Rotation(math.radians(90.0), 4, "X")    # X4 -> Blender
AXIS_TO_XAC     = Matrix.Rotation(math.radians(-90.0), 4, "X")   # Blender -> XAC
blender_to_xac_vector(v) = (v.x, v.z, -v.y)
```

导出时会套一次 `(x, z, -y)`。我此前直通传入，等于整体绕 X 轴多转了 -90°，
肢体朝向因此反了（动作时手臂朝后弯）。

试过传入 `(x, z, -y)` 想抵消，结果反而把身高推进了 Z 轴
（实测 `Y[-14.4, 19.3] Z[-161.0, 0.8]`），是**倒退**，已回退。

**结论：直通 `(x, y, z)` 是正确解**（实测 `Y[-0.8, 161.0]` = 身高）。
导出后的坐标与原版完全同构：

```
rose_head_face   X[-15.2, 16.5] Y[138.3, 179.7] Z[-12.7, 18.7]
原版 head        X[ -9.6,  9.6] Y[145.4, 182.0] Z[-10.1, 12.9]
```

### 8.3 手指被拉长：减面过度

手部原减面比例 0.30，而手指是细长结构，Collapse 减面在这种拓扑上损失最大。
已放宽到 **0.55**，手部顶点 1613 → **2762**（+71%）。

### 8.4 当前状态

| | 第二版 | 现在 |
|---|---|---|
| 手部顶点 | 1,613 | 2,762 |
| 眼球网格 | 1001（含多余镜片壳） | 500（只有真眼球） |
| 材质数 | 35 | 32（丢弃 3 个 shader 覆盖层） |
| mod 大小 | 31.0 MB | 29.5 MB |

**遗留**：`shader_eyes_shader` 的 albedo 本身偏浅（平均 162,141,137，
最亮 189，几乎没有纯白），所以眼球可能仍偏灰白。RE8 靠 shader 参数
（虹膜色/瞳孔）出效果，X4 的材质系统只认 diffuse/normal/smooth 三张图，

## 十、坐标系统重构（用户要求「重新审视」后）

前十轮我一直在「改一点→打包→等实测」，且多个诊断脚本自身有错，导致被错误结论反复带偏。
这次按用户要求做了彻底审计，结论如下。

### 10.1 三个真实且独立的 bug

**(a) 缩放丢失** —— 网格被压成 ~2 cm

```python
q = re8_to_x4(p, 1.0)          # 单位缩放，val = 米
new_verts.append((q[0]*s + o[0], ...))   # s 由 fit_segment 拟合
```

`fit_segment` 拿「米」的值去和「厘米」的骨骼位置做最小二乘，量纲不一致，
拟合出 `s≈104` 而实际需要的是 ~100 且 offset 全错。已加断言防复发。

**(b) 坐标变换被应用两次** —— 定位方式：追踪单个顶点走完全流程

```
RE8 源 (m)   = (0.387, 1.015, 0.372)
stage1 存储  = ( 39.3,  26.9, 103.6)   ← 身高在第 3 分量
Blender 骨骼 = ( 43.4,   6.8,  98.3)   ← 身高也在第 3 分量 ✓
```

两边身高轴其实**一致**，`fill_slot` 应当直通。我此前在那里套了 `(x,-z,y)`，
把身高推到 Y 轴并镜像 → 137 cm 误差。

**(c) `fit_segment` 的分段仿射拟合是混乱之源**
它按身体部位分别最小二乘，且混用两套轴序。**已整体替换为单次 Kabsch 刚性对齐**。

### 10.2 Kabsch 替换后的映射质量

```
scale = 1.034，t = (0.00, -7.30, 1.92)
Head   -> 差  2.5 cm   ✓
L_Foot -> 差  6.9 cm   ✓
Hip    -> 差  8.3 cm   ✓
L_Hand -> 差 41.9 cm   ✗
L_Toe  -> 差 23.8 cm   ✗
```

**头、躯干、腿全部映射准确，只有手和脚趾偏离** —— 这不是坐标系问题，
而是**姿态差异**（X4 手骨在 Y=6.8 身前，萝丝的手在 Y=-30）。
